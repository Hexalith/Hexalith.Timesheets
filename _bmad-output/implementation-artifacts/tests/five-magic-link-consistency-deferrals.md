## Decision guarantees

- The Time Entry owner serializes use, revocation and expiry, checks persisted terminal history and folds current owner facts. An issuance-only capability read cannot reopen a terminal owner, and an HTTP intent made before a correction cannot override the corrected scope. The processor commits use and effect in one owner result.
- A command uses the tenant catalog snapshot loaded and validated during actor processing, including across awaited authorization. A later catalog update affects subsequent decisions. `Fresh` establishes neither latest-source visibility nor a transaction across the capability, Time Entry and catalog aggregates. A second read alone would not establish either guarantee.
- Project restrictions govern tenant-owned Activity Type selection for new issuance and adjustment. Historical confirmation retains the recorded tenant-owned Activity Type policy, including after deactivation or Project exclusion. A Work target does not provide a Project identifier and triggers no inferred Project lookup.
- The canonical catalog carries tenant-bound restriction materialization. A complete tenant rebuild can establish an empty, verified unrestricted snapshot. Legacy/missing/incomplete/malformed/foreign evidence cannot grant Project selection. Contributions retain their actual source aggregate identifier; conflicting sources for one Project fail selection closed because the command contract establishes no authoritative restriction stream identity.
- The catalog handler uses the SDK's tenant-scoped epoch protocol. Named owner-sequenced deliveries are backpressured while a rebuild is Building; they retry after promotion. Accepted pending work is journaled and recoverable. Selected-generation reads refuse pending, stale or degraded evidence. The canonical store, projection, slot and logical v1 address remain unchanged; SDK-selected physical generations replace direct publication. A legacy direct catalog requires an authoritative fenced rebuild rather than an inferred migration.
